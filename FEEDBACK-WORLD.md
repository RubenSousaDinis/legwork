**2026-09-07 06:05 UTC · spike S1 — the World ID Router on Base Sepolia · hard to test** — probed the deployed Router at `0x42FF98C4E85212a5D31358ACbFe76a621b50fC02` with a `verifyProof` staticcall carrying all-zero arguments, because the cloud Selfie Check path never produces an onchain proof for action `legwork-worker` and a Base Sepolia builder has nothing else to feed it · the Router answers — `groupCount()` is `2` — and then refuses in two different ways: `routeFor(0)` itself reverts `GroupIsDisabled()` (`0x4ac73bb8`), so group 0 is switched off on this chain, and the group-1 verifier `0x163b09b4fE21177c455D850BD815B6D583732432` reverts `NonExistentRoot()` (`0xddae3b71`) because an all-zero root is not in the bridged root history. ## (3) Sandbox App states, proof flows, test users, errors, and edge cases

**2026-09-07 22:38 UTC · any sandbox error — the first live verify on a phone · broken** — opened the mini-app in World App from the Portal preview link and tapped `Verify with World ID`; the mini-app requests `selfieCheckLegacy` with `allow_legacy_proofs: true` against RP `rp_3f077b0f8979b78d`. The World ID request opened and the Selfie Check completed inside World App · back in the mini-app the landing screen re-rendered with the raw code `verification_disabled` — the widget's `onError` code, rendered as-is — above the card, and no verified state. The API's `POST /idkit/verify` was never reached, so the refusal is upstream of the cloud call: a World-side refusal at the verify endpoint surfaces here as `400 invalid_request`, which is not what the phone showed. `verification_disabled` is in none of the three places it could be — not in the IDKit error-code reference (docs.world.org/world-id/idkit/error-codes lists `user_rejected`, `credential_unavailable`, `world_id_4_not_available`, `invalid_network`, `inactive_rp`, `unknown_rp`, `invalid_rp_signature` and no `*_disabled`), not in `@worldcoin/idkit@4.2.3` or `idkit-core@4.2.4`, and not in our own code — so it comes from the World App bridge · screenshot pending · document `verification_disabled` in the error-code reference and say what disables the verification (RP state, legacy-proof policy, or credential type); from the app side, a Selfie Check that completes and then returns a code that exists in no reference is indistinguishable from a broken integration · id `E5`

**2026-09-07 22:40 UTC · any sandbox error — a second attempt on the same phone · hard to test** — tapped `Verify with World ID` again on the same device, same app, minutes after the first attempt · the landing screen came back with no error code and no verified state — the widget returned neither a result the mini-app could forward nor an `onError` code it could display, so the second attempt was silent where the first was at least wrong · screenshot pending · answer every request with either a result or a code; a silent close leaves an integrator with nothing to log. `onError` does carry an `IDKitDebugReport` as its second argument, and that report is the only place World App says *why* — the mini-app dropped it on this run and now renders it under the code. Naming that report on the error-code page would have put the reason in the first failure line rather than in a hotfix after it · id `E6`

**2026-09-08 09:55 UTC · any sandbox error — the debug report names the credential · broken** — retried `Verify with World ID` on the same phone with the mini-app now rendering IDKit's `IDKitDebugReport` beside the code, to find out what `verification_disabled` means · the report says which credential was refused: `mini_app · request f0307e6f-40e4-4d56-976e-a71a668661a2 · {"status":"error","error_code":"verification_disabled","description":"verification_disabled","version":2,"verification_level":"face"}`. So the request World App refuses is the **face** credential — Selfie Check — and it refuses it as *disabled* rather than unavailable for this user, which reads as an app-level permission rather than a credential this person lacks. There is nowhere in the Developer Portal to turn it on: World ID Configuration shows the App ID, the RP ID, the signer address, a key rotation and a danger zone, and nothing else; Mini App Permissions covers additional domains, payment addresses, Permit2 tokens, contract entrypoints and notification volume, and no credential types. `description` repeats the code rather than explaining it. The answer is in the documentation, two pages away from the error: Selfie Check (Beta) "is access-gated. To use it, request access so the feature flag can be enabled for your app" (`docs.world.org/world-id/credentials/11`), and the sandbox guide repeats it — "Selfie Check (Beta) must be enabled for your app before you can test it. To enable the feature flag, request access through your World point of contact". Neither page names the code an app gets when the flag is off, and the error-code reference does not carry it, so the one string the integrator actually sees connects to none of the three · screenshot pending · say on the Selfie Check page how an app is granted the face credential and where that grant is visible in the Portal, and make `description` carry the reason — as it stands, an integrator whose Selfie Check completes and then returns `verification_disabled` has no way to tell a missing app permission from a broken integration, and the only lead is a field inside a debug report that is not mentioned on the error-code page · id `E8`

**2026-09-08 10:20 UTC · Selfie Check as a product claim · confusing** — read the credential page to decide what the mini-app may claim about a worker, since the whole product rests on one worker being one person · Selfie Check (Beta) is "a medium-assurance biometric credential using the device camera for liveness and facial similarity" and explicitly does not guarantee "strict one-person-one-account uniqueness like Orb verification". That is the opposite of what a reader takes from the words *selfie check* and from the surrounding marketing, and it is the difference between a product that may say "one account per person" and one that may not. We had built the sentence "Verified human ✓ · World ID · one account per person" on a credential that does not support it, and moved the demo to Orb once the face credential turned out to be gated · screenshot pending · put the uniqueness sentence in the first paragraph of the Selfie Check page and in the IDKit preset reference beside `selfieCheckLegacy`, not below the fold — an integrator picking a credential is choosing what their product is allowed to claim, and that is the sentence that decides it · id `E9`
